# Beam frontend overhead reproduction

See the [local validation example](RESULTS.md) for measured residual overhead
using the generated standard MoE model.

This branch starts from JiusiServe/vllm-gr `main` at `142b8b2` and retains the
three generic changes proposed in upstream PRs
[#630](https://github.com/JiusiServe/vllm-gr/pull/630),
[#631](https://github.com/JiusiServe/vllm-gr/pull/631), and
[#632](https://github.com/JiusiServe/vllm-gr/pull/632): columnar Beam output with
optional binary replies, constrained partial TopK, and Decode graph reuse across
batch sizes. The remaining code is a standalone benchmark.

One additional generic gRPC fix forwards the configured candidate width into
the Beam request. CUDA geometry is expressed as an initial expansion matching
the first retained width, followed by the configured per-parent K. This allows
the large dynamic Beam request below to pass admission without adding fields
to the protobuf schema. The original `main` conversion left K unset and rejected
`beam_width=1024` before execution.

The benchmark generates a standard Qwen3 Dense or Qwen3 MoE configuration, an
integer-only synthetic three-token catalog, and deterministic random prompt IDs.
vLLM's `dummy` loader initializes weights locally. No checkpoint download,
tokenizer, external catalog, custom model class, model adapter, or business
features are required. The random model is for execution and latency testing;
it is not an accuracy evaluation or a pretrained-model performance claim.

## Setup and run

Install the CUDA runtime described in [the quickstart](../../docs/quickstart.md).
The validated environment uses vLLM 0.30.0 and an H20. Run from the repository
root with an idle, assigned GPU. Do not change another checkout's editable
installation: the harness sets its own `PYTHONPATH` for server and Worker.

```bash
export CUDA_VISIBLE_DEVICES=0
export PYTHONPATH="$PWD"
python benchmarks/beam_frontend_overhead/run.py \
  --output ./benchmark-output/tiny \
  --tiny --lengths 65 --batches 4 \
  --result-widths 64,1000 --samples 10 --control-samples 5
```

The full public reproduction uses 12 standard decoder layers, hidden size 1024,
and, for MoE, 32 experts with four selected per token. The tiny preset uses two
layers and a smaller hidden size. All dimensions are generated by `assets.py`.

```bash
python benchmarks/beam_frontend_overhead/run.py \
  --output ./benchmark-output/moe \
  --architecture moe --lengths 65,4097 --batches 1,4 \
  --result-widths 64,256,1000 --samples 300 --control-samples 100

python benchmarks/beam_frontend_overhead/run.py \
  --output ./benchmark-output/dense \
  --architecture dense --lengths 65,4097 --batches 1,4 \
  --result-widths 64,256,1000 --samples 300 --control-samples 100
```

Choose a fresh output directory for each independent start. Keep all starts and
slow samples when aggregating; there is no threshold that filters slow calls.
Increase `--startup-timeout` if first-use JIT compilation takes longer. Adjust
`--gpu-memory-utilization` for the assigned device.

## Serving and workload

- A real gRPC server binds to loopback. Requests traverse the production
  frontend, native EngineCore IPC, scheduler, CUDA Worker, constrained Beam
  search, terminal output, and gRPC reply.
- One explicit batch is in flight. No separate batcher or proxy is involved.
- Native `max_num_seqs` equals the largest requested input batch (four for the
  default B1/B4 run). GR owns Decode Beam expansion; it is not counted as
  thousands of native input requests. `length_penalty=0` is explicit.
- BF16, TP=PP=1, no quantization, prefix caching off. In-request KV remains
  necessary for Attention. No result-cache layer is added.
- Three generated tokens, `W=[256,512,1024]`, Beam capacity 1024, and configurable
  final `result_width`. The current public gRPC interface uses the engine's
  `constraint_table.candidate_width=256` at each stage. It does not expose
  stage-specific per-parent K in the protocol.
- The catalog has 256 first tokens, 32 second tokens per prefix, and normally
  128 final tokens. One final row has 8192 candidates. This produces a large
  candidate work capacity without a large artifact or external data.
- Default execution: eager Prefill and GR Decode CUDA Graphs. All requested
  shapes are warmed before measurement. Decode captures/replays are counted;
  the measured window must contain replay and no new captures.
- `--prefill-mode compiled` requests vLLM compilation and native Prefill graphs.
  This is a separate execution mode with longer startup; use a fresh process.
  The same Decode schedule is retained between requests. PR #632 only caches
  batch changes within a compatible schedule; this script does not exercise
  the schedule-switch issue discussed in upstream #599.
- Default and binary replies are both measured. The client consumes identical
  int32 token and FP32 score arrays, and checks repeated/default/binary outputs.
- Python's normal GC policy remains in effect. The benchmark does not freeze,
  disable, or manually collect the serving heap.

## What the timings mean

The main report uses only three timing metrics, each shown as mean / P99:

| Metric / field | Boundary |
| --- | --- |
| Pure Forward / `forward_ms` | Sum of six CUDA intervals: three model executions and three Trie/TopK/Beam selections; includes input preparation, LM head and idle gaps inside each interval, excludes gaps between intervals |
| E2E / `e2e_ms` | Client RPC call start through complete protobuf response return; includes RPC encoding/decoding, transport and server handling; excludes request construction and subsequent business/array conversion |
| Outside / `outside_ms` | The same request's `e2e_ms - forward_ms`; includes scheduling gaps between intervals, interval-external request processing, IPC, result handling and communication |

CUDA events are preallocated. No synchronization, file writes, or control RPCs
are inserted into the timed GenerateBatch calls. A separate excluded control
RPC drains the six pairs after the measured batch.

Auxiliary diagnostics are separate from the main performance table:
`client_conversion_ms` measures post-RPC array conversion/validation;
`arrays_ready_ms` includes that conversion after E2E; `probe_off_e2e_ms` comes
from separate RPCs with event recording disabled. The latter checks observer
effects and has no paired Forward measurement. These are saved under each
cell's `diagnostics` and in `diagnostics.csv`.

Every timing field reports the arithmetic mean and P99 over all its samples,
using NumPy's linear percentile interpolation. Outside-stage P99 is calculated
from the per-request differences, not by subtracting the two P99 values. Keep
sample counts with the numbers: short smoke runs provide only a coarse tail
estimate. The defaults use 300 paired and 100 probe-off calls per cell; this is
still a finite-sample diagnostic, not a production tail-latency guarantee.

CUDA intervals can include CPU launch gaps while the device waits inside a
stage. Outside time is not pure frontend time. The public standard-model
workload demonstrates interval-external cost, but it is not an equal-workload
comparison against another framework. Earlier reports labelled `RPC through
arrays` included post-RPC conversion and used a native capacity of 4096; those
measurements must not be relabelled as the E2E boundary or configuration above.

`frontend_probe.py` is a benchmark-only Worker extension. `server.py` adds a
loopback control service for configuring/draining that probe. Neither changes
the normal serving entry point or production protocol. The measurement schema
and pair counts fail closed if the expected three-stage path is not observed.

## Outputs

- `model/config.json`, `catalog.safetensors`, `gr.json`: generated public assets.
- `server.log`: startup, selected implementation, and error diagnostics.
- `summary.json`: environment, exact launch command, raw paired samples, output
  hashes, graph counters, unpaired probe-off controls, means, and P99 values.
- `metrics.csv`: one row per configuration, with explicit `_mean_ms` and
  `_p99_ms` columns for Forward, E2E and Outside.
- `diagnostics.csv`: client conversion and probe-off controls, separately.

Report the device, architecture/preset, execution mode, revision, sample count,
wire format and mean/P99 for all three timing metrics together. A tiny-model run verifies the
path and can expose host overhead; it does not predict a larger model's latency.
